## Service Design

`create_workflow()` receives the current signed-in user, workflow values, and
the SQLite database path.

Before saving, it:

1. Rejects an inactive session user.
2. Reloads the saved account from SQLite.
3. Rejects a missing, inactive, mismatched, or unauthorized saved account.
4. Normalizes submitted strings.
5. Rejects blank workflow IDs and names.
6. Rejects statuses outside the defined workflow-status allowlist.
7. Assigns the current UTC timestamp to both `created_at` and `updated_at`.
8. Sends only the validated typed workflow record to `insert_workflow()`.

## Security Decisions

- Workflow creation is protected by an explicit named permission:
  `workflows.manage`.
- The permission is granted only to administrators.
- Viewer accounts remain denied without a separate exception.
- The service does not trust an old in-memory account record by itself.
- The saved user account is reloaded before creating a workflow.
- The saved account ID must match the current session account ID.
- A deactivated or role-changed account cannot create a workflow.
- Workflow status is normalized and checked against server-side constants.
- Invalid input is rejected before a repository call can create data.
- Timestamps are generated by the server rather than trusted from user input.

## Quiz — Questions and Answers

1. Why does ABAP use a service layer before writing workflows to SQLite?

   The service applies business rules, authorization, normalization, and safe
   timestamp creation before the repository performs database work.

2. Why is `workflows.manage` an explicit permission?

   Explicit permissions support default-deny authorization. A user may manage
   workflows only when ABAP grants that exact capability.

3. Why does the service reload the saved user account?

   A session object can become stale after an administrator changes the saved
   account. Reloading prevents a deactivated or role-changed user from
   creating a workflow.

4. What does account-ID matching protect?

   It prevents a mismatched or manipulated in-memory account object from being
   treated as the saved account that owns the workflow.

5. Why is workflow status normalized with `casefold()`?

   It treats values such as `DRAFT`, `Draft`, and `draft` consistently before
   checking the server-side allowlist.

6. Why are timestamps generated by the server?

   The server provides a reliable, consistent audit time instead of trusting a
   timestamp supplied by a browser or external client.

7. What happens when a viewer calls `create_workflow()`?

   The service returns `False` and does not create a workflow because the
   viewer lacks the `workflows.manage` permission.

8. Why is the Workflow Automation dashboard card still Planned?

   The backend foundation is ready, but protected browser routes and forms do
   not yet exist for users to manage workflows through the dashboard.
